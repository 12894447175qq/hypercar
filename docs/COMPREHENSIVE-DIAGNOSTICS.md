# 一次安装综合诊断（50008）

此包把取源、传输、解码和实车观察放在一个流程里。手机预检和本地测试不能代替 MIB3 实车显示验收。

## 使用步骤

1. 安装本包，保留 vivo/Jovi，设置中选择 `com.baidu.carlife.vivo`、启用 CarLife 联动，车型选 Audi MIB3。按现有流程启动 Shizuku 并授权 Hypercar，供六端口 UID 核验使用。无需 ADB，也不需要禁用原厂应用。
2. 停止普通连接，进入“诊断 → 一次安装综合诊断”，点击“新建并开始手机预检”。采样期间保持手机解锁。整个预检可能需要数分钟，可以随时停止。
3. 程序绑定原厂来源、核验六端口、完成 CarLife 握手，采集真实视频；随后使用同一段视频依次运行五种方案。预览图片来自视频解码，不能由等待页或截屏代替。
4. 检查预览。如果是 Jovi 桌面，选择“是正常 Jovi 桌面”；若是协议提示、黑屏或解码失败，保留原状并导出诊断包。用户协议仍由你在原厂界面决定。
5. 到车旁停车后，连接车机蓝牙和车机热点，打开综合诊断并“开始 A → E 车机轮测”。每轮独立建立连接，车机可能需要重新选择 Apple CarPlay。程序会提示当前方案。
6. 每轮根据**车机实际画面**选择“正常 Jovi / Hypercar 等待页 / 黑屏 / 卡住或断开”。选完自动结束本轮并进入下一轮；90 秒未观察不能判为通过。本地被阻塞的方案不会冒充正常候选。
7. 对显示正常的方案，点击“音视频 / 触控验证”，播放声音、操作车机界面并观察约 3 分钟，分别记录声音和触控结果。停止后再点击“再连接验证”，重新确认车机画面。随时可以停止，未完成项目保留未确认。
8. 确认可用后，可以“保存已确认的显示策略”。这只保存视频策略。需要回退时点“恢复默认视频策略”。最后停止测试并“导出本批次 ZIP”，把下载目录 `HyperCar` 下的 ZIP 发回分析。

## 五种方案

| 方案 | 行为 | 判断边界 |
| --- | --- | --- |
| A 原始转发 | 保留原始 H.264，参数走独立配置包 | 普通连接缺省行为 |
| B Level 4.0 兼容 | 对可解析且满足已核查尺寸、帧率、参考帧等约束的较低等级 SPS 调整 level；更高等级保持原值 | 不改 profile，不等于重新编码；未据此宣称完整码率合规 |
| C 关键帧携带参数 | 每个 IDR 同时携带当前 SPS/PPS | 配置与帧内参数一致 |
| D 两项组合 | B + C | 同上 |
| E 硬件重编码 | 手机硬件解码器 → Surface → 硬件 H.264 编码器 | 车测目标尺寸等待车机协商；预检按来源尺寸检查硬件通路。设备拒绝配置、队列满、输出超时则明确阻塞 |

手机预检实际使用生产视频泵、屏幕封包和加密，通过真实回环 TCP 接收、校验解密后再次解码。A–D 比较原始与接收端解码像素；E 不要求有损重编码像素逐字节相同。全部结果都保留“实车待确认”边界。

## 诊断包内容与容量

- `batch.json`：批次、每个方案、用户观察、声音/触控/重连结果。
- `session.txt`：日志脱敏后的本轮可保留历史；已有文件日志采用滚动容量限制，超出历史会轮转。
- `session-parameters.json`：本轮原生代次、策略、尺寸设置、开始时间、电量及电池温度；不包含配对身份文件。
- `source.packets` / `outgoing.packets` / `transport.packets`：来源、发送端、独立回环接收端的 H.264 片段；配套 JSON 记录实际 SPS、帧数、容量或写入错误。
- `preview/first.png`、`last.png`、`decode.json`：真实解码图片、实际解码器和逐帧像素摘要。
- `transport-wire.json`：回环解密、帧时间戳、帧内参数观察。
- `outcome.json` / `validation.json`：实车轮次结果及稳定观察时间。未知、取消、断开分别记录。
- ZIP 内 `manifest.json`：所有证据文件的 SHA-256 和长度。

原生每个片段最多 90 包、实际采样最多 2 MiB（读取格式上限 8 MiB，单包上限 4 MiB）；硬件转码输出片段最多 8 MiB。只保存完整来源片段，来源断开后不把等待页混入该样本。达到采样容量后停止复制视频证据，正常传输继续。

每批次最多 128 MiB，开始阶段前预留空间；仅保留最近三个本应用批次。录制不会自动上传，导出拒绝符号链接、越界路径和身份密钥文件。硬件转码队列限制为 64 个输入包且总量不超过 8 MiB；输出桥最多四包。诊断和重编码会增加处理量，不据短时电量读数宣称节电。

## 实现与验证边界

- 保留前台保活、来源权限检查及六端口 UID 校验；不强停、卸载或禁用 vivo/Jovi。
- 诊断独占连接，普通自动重连不插入轮测；原生、编解码任务退出后才开始下一轮。代次、用户观察轮次标识均隔离；进程重启不会自动接车。
- 控制握手完成后有限重申资源，处理控制响应中的 iAP 字节；控制事务失败保留媒体，由心跳判断失效。关键帧请求限频、限次，直接模式使用暂停/启动请求，只有实际 IDR 才记录观察到恢复。
- 本地自动测试包括生产泵/TCP/加密/解密、独立 FFmpeg 像素对比、批次顺序与取消、归档校验、既有 Android/Rust 回归。合成 H.264 fixture（测试样本）不是当前手机采样。
- 未在本机运行 Android 系统或真实 vivo 编解码器；硬件编解码、原厂画面内容、MediaStore 导出、MIB3 显示/声音/触控/重连由同一 APK 的设备测试完成。Windows Hub 的 GUI 平台依赖不能在 macOS 验收。
- 默认策略仍是 A。提供的是综合验证与兼容能力，不表示这辆 MIB3 已经通过最终验收。
