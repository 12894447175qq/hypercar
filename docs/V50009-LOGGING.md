# 50009 日志覆盖与读取方法

进入「诊断 → 一次安装综合诊断」测试，结束后导出该批次 ZIP。批次关键记录与每轮协议日志独立落盘，普通日志暂停或清空不会删除这份证据。普通连接仍沿用原有日志开关。

## 已补齐的记录

| 流程 | 证据 |
| --- | --- |
| 启动与环境 | `environment`：型号、ROM、Android/API、应用版本、来源包、来源是否安装、权限检查结果、车型、Shizuku 和联动开关 |
| 每个步骤 | `timeline.txt`：开始、成功、失败或取消，墙钟时间、单调时钟、耗时、进程标识、批次、方案、案例及原生 generation |
| 蓝牙、MFi、Wi-Fi、发现、SETUP/RECORD | 原有协议消息现在按当前案例分别保存，不与其他轮次争用全局滚动文件；起始握手另外保留 |
| 来源与发送 | 首批来源帧、每 5 秒的帧数/FPS/码率/来源绑定/音频状态；关闭原生任务后核对样本是否存在、实际文件长度、帧数、SPS、closed/error/limited |
| 手机解码 | `preview/decode-attempt.json`：成功、失败或取消都记录。包含具体阶段、解码器、配置尺寸、输入数、实际出图数、输出格式、耗时和异常原因 |
| 硬件转码 | 请求尺寸和格式、硬件候选是否支持、实际配置、已送入解码器/已输出到 Surface/已编码输出三种计数、队列与峰值、首次输出时间、关键帧请求、每 5 秒进度、结束摘要、厂商错误码和 JNI 输出拒绝 |
| 断开与恢复 | `connection.failed/disconnect`、原生状态、主动停止请求；等待连接任务、编解码器、原生任务和绑定退出的步骤与错误 |
| 用户验收 | 来源是否为 Jovi、每轮车机画面、声音/触控/重连结果及策略保存请求。不会把写出了视频帧自动当成车机显示成功 |
| 进程退出 | Java 未捕获异常记录到批次；重启保留历史证据和上次忙碌阶段。半截日志行与已知临时元数据保留为不完整证据，后续新记录另起一行 |
| 导出 | 记录导出准备、实际写入步骤及错误；ZIP 清单包含文件 SHA-256，已知 `.json.tmp` 文件标记 `incompleteWrite=true` |

## ZIP 中的文件

- `timeline.txt`：每行一个 JSON 事件。先按案例和 generation 看第一条失败，再看失败前后的步骤。
- `journal-summary.json`：每个案例的首个/最近失败、协议总字节数、滚动裁剪标记、遗漏事件数及写盘错误。
- 每个案例下的 `protocol-start.txt`：最前面的 32 KiB，保留初始化握手。
- 每个案例下的 `protocol.txt` 与 `protocol.txt.1`：最近两个 256 KiB 协议片段。超过容量后中间细节可能被覆盖，摘要会标明。
- `decode-attempt.json`、原有 `decode.json`、图片、视频样本、`batch.json`、`outcome.json` 和 `validation.json` 继续保留。
- `session.txt` 是普通滚动日志的补充快照。即使它为空或只有尾部，独立批次记录仍可用于排查。

关键时间线最多 1 MiB，达到容量后用摘要明确记录遗漏数，仍保留每例首个/最近失败。异常链和堆栈有长度限制，截断数量会标明。每批次总容量和最近三批保留策略继续生效。日志中的密码、配对码、token 等字段脱敏；原始车载画面仍是用户请求采集的本地证据，不自动上传。

ZIP 是导出开始时的一致性快照，所以其中最后一项可能是 `export.write.started`；这不代表车辆流程卡在该处。导出完成或失败的后续事件保留在手机，下次导出可看到。

## 仍需真实设备判断的部分

本次不能补回旧版本从未记录的内容，也不能凭手机发送计数得知 MIB3 内部解码器状态。`decodedToSurface` 表示手机解码输出，`output` 表示手机编码输出，`sourceFrames` 表示来源帧已提交发送；实际车机画面、声音和触控必须结合用户验收结果。

原厂组件、六端口 UID 核验、连接策略和原生协议均保持原实现。本轮修改 Android 侧记录、异常报告与导出兼容，不禁用 vivo/Jovi，也不要求重连 ADB。
