# vivo / Jovi 与 Audi MIB3 测试状态

交付版本：`0.1.1 / 50000`。本地 45 项测试通过、Lint 无错误，尚未完成本版手机安装、
日志导出回读及 MIB3 实车验收。安装和日志操作见[真机测试说明](DIAGNOSTIC-LOGGING.md)。

## 已实现

- 显式选择 `com.baidu.carlife.vivo`，不会自动切换公版或小米组件。
- 按原厂 SDK 271+ 的方式绑定连接服务，每轮使用独立 Intent action，避免复用旧 Binder
  导致 Jovi 渲染参数没有送达；取消和退出释放本轮绑定。
- 冷绑定被拒绝时最多唤醒一次所选原厂 Activity，再按 SDK 节流等待后重试。
- Audi MIB3 默认首试 20 字节 MFi 挑战；已连接车机热点时仍执行网络绑定、控制服务公告和发现，
  发现有效服务后可推进，不强制等待 `0x4301`。
- 增加蓝牙触发、服务启动、来源绑定、网络、首帧和资源清理日志，并保存为文件。

## 仍需解决的阻塞

此前手机组合为 `com.baidu.carlife.vivo 8.8.4 / 273` 与 Jovi `6.0.8.3 / 6083`。
曾在 20 秒内取到 143 帧 H.264，严格解码和本地加密转发一致性通过；实际画面仍是原厂协议提示，
不是可用的车载桌面。原始采样与临时排查文件已按用户要求清理。

当前原厂实现有两处需要区分：

1. 完整 `wd.m`（Carlifeboot）流程负责原厂授权、权限检查和设备会话，再设置 `po.a0` 的进程状态。
   单独绑定渲染服务不能代替这条完整流程；桌面启动还依赖 `DeviceAttachEv`。
2. 本次分析的原厂 APK 中，`po.a0.l()` 的备用权限检查把包名和权限名以相反顺序传给
   `b8.j0.b()`；因此不能把“ADB 定位授权成功”等同于“原厂授权状态已就绪”。

此前已按用户许可，为来源组件保留大致、精确及后台定位授权；没有修改协议接受标记，
也没有禁用 vivo / Jovi 组件。下一步应依据实车日志定位完整原厂初始化入口，
需要原厂协议授权时由用户在原厂界面自行完成。

## 实车验收顺序

1. 蓝牙事件是否收到，目标过滤和前台服务是否成功。
2. MFi 应答、热点凭据、网络绑定、控制公告及 AirPlay 服务发现。
3. 配对、SETUP、RECORD 是否完成。
4. vivo 来源握手、持续帧与实际桌面；编码帧也可能只是原厂提示。
5. 声音、触控、重连、取消后的清理和实际功耗。

CarDeck 成功日志可作阶段对照，不能证明本次 Hypercar 已在车机上成功。
